# Service profiles — the selected manufacturing service

A **service profile** is one pinned artifact that fixes everything an order
export consumes for one house tier: the fabrication rules a board must have been
compiled against, the BOM/CPL dialect it emits, the official template artifacts
it was checked against, and which of the house's published rules can and cannot
be checked from board data.

Loader: `worker/pcb_worker/service_profile.py`. Shipped data:
`library/service-profiles/<id>.json`. Today there is one, `jlcpcb-economic`.

## Why a third file

Three id spaces were already in play:

| space | lives in | says |
|---|---|---|
| fab-rule profile | `library/profiles/jlcpcb-2layer.json` | the manufacturing floor a board's geometry is compiled against |
| CSV dialect | `assembly_outputs.PROFILES` | which columns the BOM/CPL carry and what a house calls its catalogue |
| service tier | `library/service-profiles/jlcpcb-economic.json` | what a person actually buys |

Assembly keys cannot be folded into a fab-rule profile:
`manufacturer_profile._load_profile_file` rejects an unknown top-level key and an
unknown floor key by design, so a rule profile carrying a BOM dialect refuses to
load. The service profile is therefore the **one selectable identity**: it names
the fab profile, and it owns the dialect numbers that used to be Python defaults
on `HouseProfile`. There is exactly one place each fact is written.

## Two selectors, one file

| selector | claims | runs the service checks |
|---|---|---|
| `jlcpcb-economic` | the Economic tier | yes |
| `jlc` | JLCPCB's CSV dialect, no tier | no |

Both emit identical bytes; the difference is what is claimed. `jlc` is kept
because a mid-layout quote export against a board not yet compiled for any house
is legitimate and must not be dressed up as orderable — the DCR's readiness
states. It is also the default of `minerva_pcb_export_assembly`, so an export
that names no service makes no claim about a manufacturer.

The emitted filenames are tagged with the **dialect** (`board-bom-jlc.csv`), not
the selector: the tag says what format a file is in, and every tier of one house
writes one format.

## What the profile pins

- **`fab_profile`** — the rule-profile id a board must have compiled against. A
  board compiled against anything else refuses with
  `assembly_service_fab_profile_mismatch` rather than being relabelled as ready
  for this house.
- **`dialect`** — emitted column headers, the `assembly.house_parts` key, the
  identity fields required, and the three thresholds `assembly_gates` compares
  against (`coordinate_unit`, `max_refs_per_row`,
  `min_designator_separation_mm`).
- **`service`** — the tier's own limits: which sides it populates, which board
  sizes it builds, the house's component-to-edge guidance figure, and what it
  adds to a board after upload.
- **`templates`** — the house's own sample files, by URL, fetch date and
  SHA-256, with the columns **parsed out of the workbook**. Semantic, never
  byte-equality against an XLSX, and never transcribed from the help page that
  links to it. The parsed contents live in
  `worker/tests/testdata/jlc_templates/`, regenerated by the `regenerate.py`
  beside them; the workbooks themselves are not vendored.
- **`checked_rules` / `advisory_rules` / `unchecked_rules`** — see below.

## A declared rule must exist

`checked_rules` and `advisory_rules` may only name codes that
`service_profile.IMPLEMENTED_CHECKS` actually implements, and `unchecked_rules`
may only name things that are **not** implemented. The load fails on either
violation. A profile therefore cannot claim a rule is in force when no code runs
it, and cannot keep listing a rule as unchecked once somebody implements it.

`unchecked_rules` rides back to the caller on every service export
(`unchecked_rules` in the `minerva_pcb_export_assembly` reply), each entry
carrying its reason. That is the difference between "clean" and "not looked at".

## Blockers versus advisories

An incompatibility with the **selected** service refuses. A board with populated
parts on the bottom side is not "mostly orderable" from a single-sided tier and
nothing an author does at export time makes it so.

| code | refuses when |
|---|---|
| `assembly_service_fab_profile_mismatch` | the board's `design_rules.rule_profile` is not the one the service pins |
| `assembly_service_side_unsupported` | a POPULATED placement sits on a side the tier does not place on |
| `assembly_service_board_size_unsupported` | the board's outer rectangle falls outside the tier's single-board size range |

Everything the house itself words as a suggestion advises instead, alongside
what the pipeline could not measure:

| code | reports |
|---|---|
| `assembly_house_component_to_edge` | a populated part's body box closer to the rim than the house suggests |
| `assembly_house_tooling_holes` | the house adds tooling holes to this tier after upload — a physical modification the package does not describe |
| `assembly_service_unmeasurable` | a non-rectangular outline, or a part whose footprint draws no body to measure |

The component-to-edge basis is the footprint's **body extent** (drawn outline
plus lands), turned by the component's own placement transform and re-boxed
axis-aligned. Re-boxing a rotated box overstates the extent, so a part at an
angle is reported slightly early rather than slightly late — the safe direction
for an advisory. It measures the **outer rim only**; interior cutout openings
are named in the unchecked list.

## The JLCPCB Economic profile

Sources, all fetched 2026-08-30 and quoted in the file's own `source` field:
[assembly capabilities](https://jlcpcb.com/capabilities/pcb-assembly-capabilities),
[BOM/CPL preparation advice](https://jlcpcb.com/help/article/advice-for-bom-and-cpl-files-preparation),
[assembly FAQs part 2](https://jlcpcb.com/help/article/pcb-assembly-faqs-part-2),
[after-sales FAQ](https://jlcpcb.com/help/article/common-pcba-after-sales-issues-and-faq).

Two things worth knowing before reading the file:

- **Header drift is real and is not resolved offline.** The workbook JLCPCB
  currently serves spells its catalogue column `JLCPCB Part #（optional）` — with
  full-width parentheses — while every exporter in circulation, including this
  one, emits `LCSC Part #`. Both spellings appear in JLCPCB's own current
  guidance. The emitted header was **not** changed on the strength of the
  template: the difference is recorded as a drift entry on the template pin and
  as `template_column_drift_resolution` in the unchecked list, and the live
  quote-page upload settles it. The same applies below the header row: the CPL
  sample writes `T`/`B` and a `mm` suffix on every coordinate, this emitter
  writes `Top`/`Bottom` and bare numbers, and JLCPCB's own guidance accepts
  either — so both halves are pinned (`observed_layer_tokens` /
  `observed_coordinate_suffix` on the template, `layer_tokens` /
  `coordinate_suffix` on the dialect) instead of one being an accident of the
  renderer.
- **No component-to-edge figure appears on the process-edge page.** The 0.3 mm
  figure this profile advises against is the Economic-specific one from FAQs
  part 2 item 14 ("We suggest that the edges of the traces and components must
  be more than 0.3mm away from the edge of the board"), stated beside the ~0.2 mm
  depanel routing tolerance that motivates it. The process-edge page publishes
  5 mm rails, 2 mm tooling holes and 1 mm fiducials for **panels** and no
  component clearance at all; nothing was invented to fill that gap.

The tier builds 2, 4 and 6 layers, but this profile pins the **2-layer** fab
rules, whose capability block caps a board at the two-copper baseline. A 4- or
6-layer Economic order needs a sibling service profile pinning the matching fab
profile — a data addition. No layer-count gate ships, because one that cannot
refuse anything would overstate what is checked.
